# 待审核问题通过后正式发布设计

## 范围

本次只修复管理端“通过”动作：人工审核通过的未收录问题必须原子地进入公开问题库，并在客户端问题卡片中可见。同时把提交结果显示在当前操作区域，避免点击后无反馈。

本次不实现多人账号、角色权限、实时协作锁、域名或 HTTPS，也不重建现有 SQLite 数据库。

## 当前问题

- 管理端目前只调用审核决策接口，将 `review_tasks` 更新为 `approved`。
- 该动作不会写入 `question_intents` 和 `canonical_answers`，所以不会生成客户端卡片。
- 提交结果使用队列底部的单一消息，长页面中无法及时看到失败原因。
- 线上“宿舍晚上几点熄灯？”仍为 `pending`，因此可以在修复部署后重新审核，不需要恢复数据。

## 目标行为

点击“通过”后，在同一个数据库事务中完成：

1. 再次确认审核任务仍为 `pending`。
2. 查找标准化问题文本完全相同的现有意图。
3. 若命中现有意图，为其创建新的正式答案版本；若未命中，创建新的问题意图。
4. 新问题默认归入 `补充问答`，不置顶，排序号为现有最大值加一。
5. 以审核后答案作为完整答案，并以其首个非空段落生成简明答案，最多 150 个 Unicode 字符。
6. 沿用审核任务已有来源；允许人工审核的问题暂时没有来源，此时公开答案的来源数组为空。
7. 创建 `published` 状态的正式答案版本及对应来源记录。
8. 将审核任务更新为 `approved`，保留审核人、说明、回流目标和审核后答案。
9. 提交事务并返回正式问题 ID、版本号以及是否新建问题。

任何一步失败都必须回滚，不能出现“审核已通过但客户端没有答案”或“答案已发布但任务仍待审核”的半完成状态。

## 后端边界

- 新增独立的“审核发布服务”接口，由 SQLite 实现负责单事务写入。
- 审核决策路由仅在状态为 `approved` 时调用该服务；`rejected` 和 `needs_more` 保持现有逻辑。
- 生产环境必须注入审核发布服务；测试中可以显式提供替身。
- 不修改现有23条答案，不删除13条审核任务，不使用种子数据库覆盖运行数据库。
- 新意图 ID 从审核任务 ID 确定性生成，重复请求依靠任务状态校验阻止二次发布。

## 前端反馈

- 提交失败信息显示在当前审核卡片内部，并保留已填写内容。
- 提交成功后移除该待审核卡片，并在队列顶部显示：问题已发布、正式版本号和客户端刷新提示。
- “通过”按钮文案改为“通过并发布”，明确该动作会影响公开客户端。
- 请求进行中禁用当前卡片操作，防止连续点击。

## 客户端行为

- `/api/questions` 继续只返回每个意图的最新 `published` 版本。
- 新问题发布成功后，下一次请求立即包含新卡片；已打开的客户端刷新页面后可见。
- 新问题的标准问法同时作为首个相似问法，使相同提问可以命中正式答案。

## 测试与验收

- 通过一个无来源的新问题后，正式问题数量增加一，审核任务变为 `approved`。
- 新卡片的问题、简明答案和完整答案与审核内容一致。
- 相同标准问题再次审核时不会创建重复意图，而是创建下一个答案版本。
- 模拟正式答案插入失败时，审核任务仍保持 `pending`。
- 重复提交同一审核任务返回冲突，不产生第二张卡片。
- 驳回和需补充仍不创建公开问题。
- 错误信息显示在对应卡片内。
- 原有23条已发布问题和其历史版本保持不变。
- 原有其他待审核任务保持不变。
- 客户端匿名提问、TokenDance 和联网搜索回归测试继续通过。

## 部署与回滚

部署前备份 `runtime/live-in-hdu.db` 并记录 SHA-256。发布代码后先用一条专用测试审核任务验收，再处理真实任务。

本次不需要破坏性数据库迁移。若代码验证失败，恢复上一个代码版本并重启 `live-in-hdu`；数据库仅在实际产生错误写入且确认需要时才从部署前备份恢复。

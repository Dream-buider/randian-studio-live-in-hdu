# LIVE IN HDU 分布式团队公网内测与技术交接设计

日期：2026-07-31
状态：已确认方案，待用户复核书面设计

## 1. 背景与目标

LIVE IN HDU 当前完整技术栈运行在开发者的 Windows 电脑上，用户端、审核后台、
业务 PostgreSQL、WeKnora、Ollama、SearXNG 和 TokenDance 网关已经完成本地联调。
首批 23 道人工审核问答已经发布。下一阶段不是立即正式上线，而是让分散在不同网络
中的老板和 20 多名团队成员通过互联网完成一次受控内测。

本阶段目标是提供一个可以直接在手机浏览器打开的 HTTPS 地址，只允许访问用户端的
问题卡片和提问能力，同时保证审核后台、审核接口、系统状态、数据库、知识库管理端和
密钥不对公网开放。测试完成后应能一键关闭入口，且不影响本地数据。

本阶段同时为后续人员交接建立明确边界：开发者完成产品和可交接的技术材料，后续技术
人员接管前后端、服务器与日常运维；开发者继续负责 LIVE IN HDU 和飞书社区的资料、
答案与内容时效。

## 2. 角色与责任

| 角色 | 本阶段责任 | 后续责任 |
| --- | --- | --- |
| 老板 | 作为真实用户验收产品，确认正式上线预算和人员 | 持有并支付服务器、域名、模型和平台账号 |
| 团队测试成员 | 使用用户端浏览和提问，提交体验反馈 | 不接触管理后台和基础设施 |
| 当前开发者 | 完成安全公网内测入口、修复内测问题、整理交接材料 | 维护社区资料、审核内容与时效信息 |
| 后续技术人员 | 本阶段阅读交接材料并了解架构 | 接管前端、后端、云端部署、备份、监控、密钥和故障处理 |

任何正式云账号和长期运行资源都应归团队或老板所有，不应长期绑定当前开发者的个人
电脑、个人密钥或个人付款账户。

## 3. 方案选择

采用“本机运行 + 独立公网测试网关 + 国内内网穿透”的方案。

- 主方案使用 cpolar 将本机测试网关映射为临时 HTTPS 地址。
- 如果当前网络无法稳定连接 cpolar，则采用花生壳作为等价替代；两者不能同时运行。
- 不直接映射现有 `3210` 端口，因为该端口同时承载用户端和未具备公网身份认证的管理
  接口。
- 不在本阶段购买云服务器，不进行域名备案，不迁移数据库或知识库。

Cloudflare Quick Tunnel 不作为主方案，因为它更适合开发测试，且国内访问体验不能
作为本次 20 多人内测的稳定前提。立即租用云服务器也不符合“先内测、老板验收后再
承担成本”的当前顺序。

## 4. 系统结构

```text
老板和团队成员
    |
    | HTTPS 临时地址 + 团队测试码
    v
国内内网穿透服务
    |
    | 只转发到 127.0.0.1:3211
    v
公网测试网关（新增，端口 3211）
    |-- 登录页和测试会话
    |-- GET  /                  用户端页面
    |-- GET  /assets/*          用户端静态资源
    |-- GET  /api/questions     已发布问题
    |-- POST /api/ask           用户提问
    `-- 其他路径全部拒绝
            |
            | 本机回源
            v
完整业务服务（现有，端口 3210）
    |-- 用户接口
    |-- /admin 与 /api/admin/*
    |-- /api/reviews/*
    |-- /api/health
    `-- PostgreSQL、WeKnora、Ollama、SearXNG、TokenDance
```

`3210` 继续作为本机完整入口；`3211` 是唯一允许连接内网穿透的端口。公网测试网关只
监听 `127.0.0.1`，不额外开放 Windows 防火墙入站端口。数据库、WeKnora、SearXNG
及 Ollama 均不直接映射公网。

## 5. 访问控制

### 5.1 团队测试码

- 团队成员第一次打开公网地址时进入简洁的测试登录页。
- 输入一个本轮内测专用的共享测试码后，服务器签发 12 小时有效的会话 Cookie。
- Cookie 使用 `HttpOnly`、`Secure` 和 `SameSite=Lax`，浏览器脚本无法读取。
- 测试码和 Cookie 签名密钥只保存在被 Git 忽略的本地环境文件中，不进入源码、文档、
  二维码或聊天截图。
- 内测结束后轮换测试码并关闭隧道，旧地址和旧会话随即失效。

测试码的目的不是代替正式账号系统，而是限制临时链接在团队范围内传播。本阶段不开发
个人注册、短信验证码、微信登录或多角色账号系统。

### 5.2 路由白名单

公网测试网关采用“默认拒绝”，仅放行：

- 测试登录、退出和会话检查；
- 用户端 HTML、图标及构建后的静态资源；
- `GET /api/questions`；
- `POST /api/ask`。

以下路径必须从公网返回 404，不暴露其存在，也不转发到 `3210`：

- `/admin` 及所有管理端静态资源；
- `/api/admin/*`；
- `/api/reviews`、`/api/reviews/*`；
- `/api/health`；
- 其他未明确列入白名单的路径和 HTTP 方法。

### 5.3 滥用与成本保护

- `POST /api/ask` 只接受 JSON，并沿用业务层非空问题校验。
- 公网网关额外限制请求正文大小，问题文本最长 500 个字符。
- 每个测试会话每 10 分钟最多提交 30 次问题；该阈值高于正常测试使用，仅用于阻断
  脚本滥用。
- 超限请求返回明确的稍后重试提示，不调用 TokenDance，也不写入审核队列。
- 日志记录时间、请求标识、路由、状态码和耗时，不记录测试码、Cookie、API Key、
  数据库连接串或完整请求正文。
- 页面继续提示用户不要输入身份证号、手机号等敏感信息。

## 6. 数据流与既有业务规则

通过公网入口提交的问题仍进入现有三段式回答流程，不为内测另建一套答案逻辑：

1. 命中预设问题，返回人工审核答案。
2. 未命中预设问题但命中知识库，返回知识库答案。
3. 两者均未命中，执行联网搜索和模型生成，返回既定甄别批注，并按服务器时间顺序
   写入 FIFO 人工审核队列。

管理员离线不会阻塞用户获得回答；内测入口只限制访问范围，不改变问题识别、回答来源、
甄别批注或审核回流逻辑。当前开发者仍通过本机 `http://127.0.0.1:3210/admin`
处理内容，不通过公网地址进入后台。

## 7. 启停与运行约束

新增脚本应提供以下操作：

- 启动完整本地知识栈；
- 启动公网测试网关；
- 启动选定的内网穿透客户端并输出临时公网地址；
- 检查用户端、白名单接口和后台拦截状态；
- 只停止公网测试入口；
- 安全停止完整知识栈，且不删除数据卷。

所有新增缓存、日志、下载文件和隧道运行文件继续放在
`D:\Star\LIVE_IN_HDU_RUNTIME`。电脑必须保持开机、联网且禁止自动休眠；Docker、
Ollama、本机网络代理、知识栈、公网网关和隧道客户端任一停止，外部访问都可能中断。
TokenDance 只提供模型接口，不能替代本机服务器。

## 8. 测试与验收

上线团队内测前必须完成：

1. 本机完整服务和现有自动化测试继续通过。
2. 公网网关的测试码正确时能够进入，错误时无法进入。
3. 手机关闭 Wi-Fi、使用 4G/5G 打开公网 HTTPS 地址。
4. 手机能够浏览 23 个问题、展开完整答案并提交一个预设问题。
5. 提交一个未命中问题时仍能得到回复，并正确进入待审核队列。
6. 从公网访问 `/admin`、`/api/admin/intents`、`/api/reviews` 和 `/api/health`
   均返回 404。
7. 不携带会话、伪造 Cookie、超长正文和高频请求均被拒绝。
8. 浏览器控制台无错误，移动端布局没有明显溢出。
9. 关闭公网入口后，外部地址不可访问，但本地 `3210` 和业务数据保持正常。
10. 密钥扫描通过，Git 中没有测试码、隧道令牌或 API Key。

团队内测建议持续 2 至 3 天。反馈按“设备与浏览器、操作步骤、预期、实际结果、截图”
五项提交到统一飞书表格，避免微信群中重复或遗漏问题。

## 9. 交付物

本阶段交付给老板：

- 可在手机打开的临时 HTTPS 地址和二维码；
- 单独发送的团队测试码；
- 一页式产品说明：解决的问题、用户流程、当前 23 问、未知问题审核回流；
- 一页式内测说明和统一反馈入口；
- 测试结果摘要，包括参与人数、问题数、失败情况和主要改进项。

交付给后续技术人员：

- 源代码和 Git 提交记录；
- 架构、环境变量模板、端口和依赖清单；
- 本地及公网测试启停脚本；
- 数据备份、恢复、日志和故障排查手册；
- 云迁移边界与尚未完成事项；
- 明确不包含真实密钥的配置样例。

当前开发者后续保留的内容维护工作：

- 维护 LIVE IN HDU 与飞书社区资料；
- 汇总团队或学生的新回答；
- 标注年份、校区、来源和时效；
- 提交或审核知识库更新内容；
- 不负责长期服务器值守、系统故障响应或个人垫付云资源费用。

## 10. 正式上云边界

团队内测通过后，再由老板决定并承担云端成本。正式阶段迁移现有业务网关、PostgreSQL、
WeKnora 和搜索能力，结合服务器配置决定继续使用本地 Ollama 嵌入模型，或改为团队
账号持有的远程嵌入服务。届时补充域名、备案、HTTPS、正式身份认证、监控、备份和
故障响应。

本次公网内测不等于正式上线，也不承诺 7x24 小时可用。其成功标准是：20 多名分散
用户能够安全体验真实产品流程，管理能力不暴露，反馈可集中回收，并形成足够明确的
依据让老板决定后续投入和技术人员接替。

# LIVE IN HDU「匹配室友」第一版设计

日期：2026-08-11

## 1. 目标与边界

在现有 LIVE IN HDU 新生问答客户端顶部，把“匹配室友”入口放在“新生指北”和“全部问题”左侧。新生收到学校寝室短信后，可以登记自己的寝室、昵称和可选联系方式，并查看同一寝室其他已登记成员的信息。

第一版解决的是“按寝室找人”，不是基于性格、作息或兴趣的智能匹配。登记提交后立即生效，由管理员事后处理异常信息。

本轮范围包括：

- 下沙校区寝室登记、同寝室成员列表和个人记录管理；
- 绍兴校区的禁用占位和可扩展地址模板；
- 联系方式隐私保护、90 天保留、重复与滥用限制；
- 现有仅管理员可访问的管理端增加独立的室友登记管理模块；
- HTTPS 启用门槛与上线验收。

本轮不包括：

- 绍兴校区真实寝室格式与提交能力；
- 性格、作息、兴趣等推荐算法；
- 学号、短信或学校身份核验；
- 客户端“联系我们”入口；
- 多管理员独立账号、角色权限和公网管理端登录；
- 按真实床位数限制每个寝室的登记人数。

## 2. 已确认的产品规则

1. 用户必须先登记某个寝室，才能看到该寝室的成员列表；知道寝室号不等于可以直接查看。
2. 这种限制只是降低随意浏览风险，不代表完成了真实学生身份认证。页面不能宣称成员身份已经由学校核验。
3. 下沙校区第一版地址结构为“楼栋 → 南/北 → 寝室号”。
4. 楼栋使用数字输入并规范显示为“11号楼”；南/北使用选择项；寝室号单独输入。
5. 绍兴校区可被选择，但只显示“寝室分配规则确认中，暂未开放匹配”，不能提交。
6. 昵称或称呼必填，真实姓名不要求填写。
7. 联系方式可不填；填写时只选择一种：微信、QQ、手机号或其他。
8. 用户填写联系方式时必须主动同意将其展示给同寝室已登记成员。
9. 一人登记时显示一人，五人登记时显示五人；第一版不把人数上限写死。
10. 同一浏览器已有有效登记时再次进入，打开现有记录供查看或修改，不新增重复成员。
11. 每条登记保留 90 天；到期后从成员列表隐藏，并清除联系方式。
12. 提交成功后生成一份高强度管理码，只展示一次供用户保存；浏览器同时获得安全会话。
13. 用户可以通过当前浏览器会话或管理码修改、删除自己的登记。
14. 普通登记立即生效，不进入现有问答审核队列。
15. 客户端第一版没有“联系我们”入口；异常记录由现有管理端事后隐藏或删除。

## 3. 方案选择

采用现有 Node/Fastify 应用和现有云端 SQLite 数据库，在应用内部新增边界清晰的 roommate 模块、独立数据表和独立 API。

不建立第二套服务，也不引入 BaaS。原因如下：

- 现有腾讯云服务器已经持续运行客户端、问答后端和 SQLite；新增模块不需要新的服务器费用。
- 同一应用部署可以复用现有构建、systemd、备份和管理端安全边界。
- 独立表和服务层可以避免寝室数据与预设问答、知识库、人工审核队列互相污染。
- 数据规模扩大后，可以在不改变客户端协议的前提下把 roommate 存储层迁移到 PostgreSQL。

本设计不修改既有问答表、知识库表或审核队列表，不重建数据库。

## 4. 客户端信息架构

### 4.1 入口

问题卡片页面顶部导航顺序调整为：

1. 匹配室友
2. 新生指北
3. 全部问题

“匹配室友”使用与现有导航一致的移动端样式，不挤压品牌标题，不影响现有页面的自适应布局。

### 4.2 三步用户流程

第一步：选择校区并填写寝室。

- 下沙校区：填写楼栋数字、选择南或北、填写寝室号。
- 绍兴校区：显示未开放说明，提交按钮禁用。
- 提交前展示规范化结果，例如“下沙校区 · 11号楼 · 南 · 207”，让用户再次确认。

第二步：填写个人展示信息。

- 昵称或称呼必填；
- 联系方式可选；
- 若填写联系方式，选择微信、QQ、手机号或其他之一；
- 必须勾选“我同意将该联系方式展示给同寝室已登记成员”。

第三步：查看同寝室列表。

- 显示规范化寝室名称和所有有效登记；
- 每位成员显示昵称；未留联系方式时显示“暂未留下联系方式”；
- 已留联系方式时向同寝室已登记成员显示类型和完整内容；
- 页面提供“修改我的信息”和“删除我的登记”；
- 首次提交成功时同时显示长期可见的登记 ID 和只展示一次的管理码，并要求用户复制保存完整恢复凭证。

## 5. 地址模板与标准化

地址解析采用校区模板注册表，不把下沙规则写成全局固定字段。

下沙模板 `xiasha-v1` 定义：

- `building`：正整数，去除无意义前导零，显示为“数字 + 号楼”；
- `orientation`：枚举 `south` 或 `north`，显示为“南”或“北”；
- `room`：接受合理长度的数字或字母数字组合，去除首尾空格，英文字母转为大写；纯数字时去除无意义前导零；
- 规范化房间标识由校区、模板版本、楼栋、朝向和寝室号共同生成。

示例：

```text
xiasha|xiasha-v1|11|south|207
```

绍兴模板只注册 `shaoxing-pending` 状态，不定义地址字段。以后拿到学校短信模板后新增 `shaoxing-v1`，不修改下沙历史记录。

## 6. 数据模型

新增三组独立数据，不复用问答审核记录。

### 6.1 roommate_registrations

每条登记至少包含：

- 随机登记 ID；
- 校区代码和地址模板版本；
- 用于精确分组的房间键；
- 用于精确管理筛选的楼栋键；
- 加密后的规范化地址；
- 加密后的昵称；
- 可选联系方式类型；
- 可选的加密联系方式；
- 用于限制同一联系方式重复登记的不可逆摘要；
- 管理码摘要；
- 联系方式展示同意时间；
- 状态：`active`、`hidden`、`deleted` 或 `expired`；
- 创建、更新、到期和删除时间。

房间键和楼栋键使用服务端密钥计算 HMAC，不直接用“11-南-207”作为公开索引。昵称、完整地址和联系方式使用带认证的对称加密保存。密钥只放在服务器环境配置中，不进入 Git、数据库或日志。

### 6.2 roommate_sessions

保存浏览器安全会话的摘要、对应登记 ID、创建时间和到期时间。客户端只持有 `Secure`、`HttpOnly`、`SameSite=Strict` Cookie，不能从 JavaScript 读取会话令牌。

修改寝室后，会话继续归属本人，但后续只能读取新寝室成员列表。

### 6.3 roommate_admin_audit

记录管理员操作：目标登记、操作类型、操作人标识、原因和时间。第一版操作人固定使用现有安全管理通道提供的 `local-admin` 标识；字段设计允许后续替换为独立管理员账号 ID。

## 7. 服务与 API 边界

roommate 模块拆成以下职责：

- 地址模板：校验、规范化和生成人类可读地址；
- 登记服务：创建、读取、修改、删除和重复判断；
- 访问控制：验证当前安全会话或一次性管理码；
- 成员查询：只返回与当前有效登记具有相同房间键的成员；
- 保留策略：将过期记录标记为过期并清除联系方式；
- 管理服务：筛选、隐藏、恢复、删除和写入审计记录。

建议 API 边界：

- `GET /api/roommates/config`：返回功能开关和校区模板的非敏感配置；
- `POST /api/roommates/registrations`：创建登记并建立会话；
- `GET /api/roommates/me`：读取自己的登记；
- `PATCH /api/roommates/me`：修改自己的登记；
- `DELETE /api/roommates/me`：删除自己的登记；
- `POST /api/roommates/recover`：使用登记 ID 与管理码恢复会话；
- `GET /api/roommates/members`：读取当前登记所属寝室的有效成员；
- `/api/admin/roommates/*`：复用现有仅服务器本机可访问的管理边界。

任何客户端传入的房间键、状态、到期时间或管理员字段都不可信，必须由服务端计算。

## 8. 创建、查看与恢复流程

### 8.1 首次创建

1. 客户端读取可用校区模板。
2. 用户填写下沙寝室、昵称和可选联系方式。
3. 客户端展示规范化地址供确认。
4. 服务端再次校验和规范化，不能相信客户端结果。
5. 服务端生成房间 HMAC、加密个人字段、生成随机管理码并只保存其摘要。
6. 服务端写入 90 天到期时间并创建安全会话。
7. 响应只在本次返回明文管理码；登记 ID 可在“我的登记”中继续查看，管理码刷新页面后不能再次读取。
8. 用户随后可读取同一房间键下的有效成员。

### 8.2 同浏览器再次进入

浏览器存在有效安全会话时，客户端直接打开“我的登记”和同寝室列表，不创建新记录。用户主动修改寝室后，列表随新房间键切换。

### 8.3 新设备恢复

用户输入登记 ID 和管理码。服务端以恒定时间方式比对摘要；成功后建立新安全会话，失败时只返回统一的“登记信息或管理码不正确”，不暴露记录是否存在。

管理码丢失且原浏览器会话也失效时，第一版无法自动找回。由于客户端不提供“联系我们”，该记录只能等待 90 天到期，或由管理员在安全管理端处理。

### 8.4 删除

用户删除自己的登记后，立即从成员列表移除并清除联系方式密文；保留最小状态记录和必要审计信息，避免旧管理码恢复已删除内容。

## 9. 重复登记与滥用控制

第一版不根据寝室实际床位数设置人数上限，避免把未知或变化的住宿规则写死。

采用以下低侵入限制：

- 一个有效浏览器会话对应一条有效登记，再次进入时只能修改现有记录；
- 同一联系方式摘要不能同时对应多条有效登记；
- 按 IP 和时间窗口限制创建、管理码尝试和成员列表读取频率；
- 管理码连续失败达到阈值后进行短时冷却；
- 对昵称和联系方式设置长度、字符及控制字符限制；
- 管理员可以隐藏、恢复或删除异常登记；
- 不采集设备指纹，不要求上传学生证或身份证。

无联系方式的恶意用户仍可能换浏览器或网络重复登记，这是未接入学校身份核验时无法完全消除的剩余风险。第一版通过限流和事后管理降低风险，不对外宣称能够彻底防止冒充。

## 10. 管理端

在现有管理页面中新增独立的“室友登记管理”，不混入问题审核列表。

支持：

- 默认按创建时间从新到旧排列；
- 按校区、状态以及管理员输入的精确楼栋或寝室条件筛选；
- 查看昵称、脱敏联系方式、创建时间、更新时间、到期时间和状态；
- 在明确操作后查看必要的完整联系方式；
- 隐藏、恢复和删除登记；
- 记录操作人、原因和操作时间。

普通用户访问管理 API 仍返回 401 或 403。第一版不新增公网管理登录，也不新增多人账号；你继续通过现有 SSH 安全通道使用管理端。后续建立独立账号时，直接把审计记录中的 `local-admin` 替换为登录账号 ID。

## 11. HTTPS 与发布门槛

室友信息包含精确寝室和联系方式，因此功能不能在当前纯 HTTP 公网地址上正式开放。

采用以下发布规则：

1. 使用计划域名 `liveinhdu.cn` 完成购买、实名认证和中国大陆服务器 ICP 备案；域名与备案主体应由老板或团队长期控制的腾讯云账号持有。
2. Nginx 监听 80/443，80 强制跳转 HTTPS，443 使用有效证书并反向代理到 `127.0.0.1:3210`。
3. Node 服务改为仅监听回环地址，公网不再直接开放 3210。
4. Nginx 正确传递协议和客户端地址，服务端只在可信代理配置下接受 `X-Forwarded-Proto`。
5. `ROOMMATE_MATCHING_ENABLED` 默认为关闭；只有域名、HTTPS、Cookie、反向代理和敏感接口检查全部通过后才开启。
6. 功能关闭或请求不是可信 HTTPS 时，创建、恢复、读取成员和读取联系方式接口一律拒绝；现有问答页面可以继续运行。
7. 室友相关页面设置 `noindex`，降低寝室信息被搜索引擎收录的风险。

域名购买、实名认证、备案和证书申请属于发布前置工作，不在 roommate 业务代码中伪造或绕过。

## 12. 隐私提示

提交页必须明确说明：

- 本功能由 LIVE IN HDU 团队提供，不是学校官方身份认证系统；
- 寝室匹配依据用户自行填写的信息，真实性需要自行判断；
- 昵称会展示给同寝室已登记成员；
- 联系方式为可选项，填写后会展示给同寝室已登记成员；
- 登记默认保留 90 天，用户可提前修改或删除；
- 不要填写身份证号、银行卡号、家庭住址等无关敏感信息。

未填写联系方式时不要求勾选联系方式共享同意；一旦填写，就必须主动勾选后才能提交。

## 13. 错误处理

- 字段缺失或格式不合法：在对应输入框旁提示，不清空其他输入。
- 绍兴校区：显示规则确认中的禁用状态，不发起创建请求。
- 重复浏览器会话：返回现有记录并引导修改，不新增成员。
- 联系方式已被其他有效记录使用：提示修改现有登记或改用其他联系方式，不暴露对方信息。
- 管理码错误或登记不存在：返回相同提示，避免记录枚举。
- 会话过期：引导使用登记 ID 和管理码恢复。
- 登记已隐藏：本人可看到状态，但不能读取成员列表；可修改后等待管理员恢复，第一版不提供客户端申诉入口。
- 登记已删除或过期：不能恢复原联系方式，需重新登记。
- 网络或服务异常：客户端保留未提交表单，允许重试，不能重复创建。
- 加密密钥缺失、解密失败或数据库异常：敏感接口失败关闭，不返回残缺或未解密数据，也不影响现有问答路由启动。

## 14. 数据保留与定时清理

每次读取成员列表时先排除到期记录；后台定时任务负责批量处理：

1. 将超过 90 天的 `active` 或 `hidden` 登记转为 `expired`；
2. 清除联系方式密文和联系方式摘要；
3. 使关联会话失效；
4. 保留最小状态、时间和审计数据，用于排查删除是否正常执行。

清理任务必须幂等，即重复执行不会破坏仍有效的登记。数据库备份也应纳入保留周期，不能让已删除联系方式无限期停留在长期备份中。

## 15. 测试与验收

### 15.1 地址与数据单元测试

- 下沙楼栋、南北和寝室号的正常化及非法输入；
- 相同规范地址生成相同房间键，不同地址生成不同房间键；
- 绍兴模板保持禁用；
- 个人字段加密后数据库中不存在明文，解密错误安全失败；
- 管理码只存摘要且比对正确；
- 90 天到期、清除联系方式和任务幂等。

### 15.2 权限与业务测试

- 未登记用户不能读取任一寝室成员；
- 已登记用户只能读取与自己房间键完全一致的成员；
- 同一寝室一人、五人以及更多有效登记都能完整显示；
- 不同楼栋、不同南北或不同寝室号之间完全隔离；
- 未留联系方式的成员仍正常显示昵称；
- 同浏览器重复提交不会新增成员；
- 新设备使用正确管理码可以恢复，错误管理码不能恢复；
- 用户只能修改或删除自己的记录；
- 修改寝室后失去旧寝室列表访问权；
- 隐藏、删除、过期记录不出现在成员列表；
- 限流和管理码失败冷却生效。

### 15.3 管理端测试

- 公网匿名用户不能读取或修改室友管理数据；
- 现有 SSH 本地管理通道可以查看、筛选、隐藏、恢复和删除；
- 敏感联系方式默认脱敏；
- 管理操作正确记录 `local-admin`、原因和时间；
- 室友登记不进入问答审核队列。

### 15.4 HTTPS 与回归测试

- HTTP 请求被跳转到 HTTPS；
- 无可信 HTTPS 时所有室友敏感接口拒绝服务；
- Cookie 同时具备 `Secure`、`HttpOnly` 和 `SameSite=Strict`；
- 公网不能直接访问 3210；
- 室友页面不被搜索引擎索引；
- 原有问题卡片、新生指北、聊天问答、TokenDance、联网检索和人工审核队列全部保持正常；
- 既有 SQLite 数据库和待审核记录在迁移前后数量及内容一致。

## 16. 部署与回滚

1. 在部署前备份当前代码、环境配置和 SQLite 数据库，并记录路径和校验值。
2. 通过只新增表的迁移创建 roommate 数据结构；迁移不得删除、重命名或重写既有表。
3. 先以 `ROOMMATE_MATCHING_ENABLED=false` 部署并完成数据库、管理端和回归验证。
4. 配置域名、备案、Nginx、证书、回环端口和环境密钥。
5. 在生产数据库副本上完成权限、到期和回归测试。
6. 开启功能开关，再从公网手机完成完整创建、查看、修改、恢复和删除流程。
7. 失败时关闭功能开关并恢复部署前代码；新增表可以保留但不对外使用。只有确认迁移本身破坏数据时才恢复数据库备份。
